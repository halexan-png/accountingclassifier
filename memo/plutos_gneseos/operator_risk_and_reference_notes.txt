FOUR THINGS AN OPERATOR SHOULD BE ABLE TO ANSWER, AND CURRENTLY CAN'T

Four behaviors of this pipeline that aren't obvious from a single run.
Every fact below was checked directly against the pipeline's code, not
carried over from memory. For what every column, flag, and deal-profile
field actually means, see Specifics -> Field Glossary.


1. A STOPPED RUN DOES NOT RESUME — IT STARTS OVER, AND CHARGES YOU AGAIN
------------------------------------------------------------

Bottom line: there is no resume path anywhere in this system. However a
run stops — a closed laptop, a crash, a deliberate Stop click, or the
spend rail tripping — whatever had already finished at that moment is
kept (it's written to disk as it happens, so it isn't lost), and
everything else is marked "not processed." Finishing the quarter means
running it again from the first row, and running it again means
reclassifying and repaying for every row, including the ones already
finished and paid for the first time. A second run is never a
continuation of the first — that's the costliest misunderstanding
available here.

What differs by trigger:

Spend rail — a backstop against a runaway bill, not a budget line. It
only fires if a run's actual cost climbs to twice its own pre-run
forecast, deliberately loose so an ordinary overrun never trips it.
Firing stops the run through the same path above; it does not refund
what was already spent.

Cancel vs. Stop — Cancel lives on the forecast screen, before a single
row has been sent anywhere; walking away there costs nothing. Stop lives
on the running screen, after spending has already begun; clicking it
isn't instant (whatever's already in flight finishes first), and it does
not undo the spend already committed.


2. ONE THING DOES CARRY OVER BETWEEN RUNS — AND IT ISN'T YOUR ROW DECISIONS
------------------------------------------------------------

The running list of known deals, built from this quarter's acquisition
and transaction activity, carries forward into every run after it — each
run adds to that list rather than replacing it, so it only grows.

Row-by-row decisions are the opposite: they never carry over. A second
run will recognize deals it has seen before, but it still re-decides,
and re-charges for, every single row. Don't confuse the two — the deal
list remembers; your classification decisions do not.


3. AN INVOICE LONGER THAN TWENTY PAGES IS ONLY PARTLY READ
------------------------------------------------------------

Up to twenty pages, the system reads an invoice in full. Past that
length, it reads only the first two pages and the last two — nothing in
between. A thirty-page invoice is read across four of its thirty pages;
the other twenty-six are never opened.

This isn't announced anywhere a person would naturally look — only as a
flag on the row itself (INVOICE_TRUNCATED — see Specifics -> Field
Glossary). A deciding detail sitting mid-document is simply never seen,
and the row is still classified as if nothing were missing.


4. A ROUGH DEAL SWEEP DOESN'T PAUSE YOUR RUN — IT QUIETLY CARRIES ON
------------------------------------------------------------

Before classification begins, the system sweeps this quarter's
acquisition and transaction rows to build its list of known deals. If
that sweep runs into trouble — some rows it can't gather information
for, or no deals found at all — the run does not stop to ask whether to
proceed. It logs what happened and carries on into classification
anyway, on the reasoning that a thin deal list is still better than
none, and that any M&A row the sweep couldn't gather is labeled
non-recurring by fixed rule regardless, not by judgment that could be
compromised.

The practical effect for an operator: nothing in the running app says so
in the moment. The recognizable-deals vocabulary available to the rest
of the run may simply be thinner than usual, silently.
